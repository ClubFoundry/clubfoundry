# Сайдкар ClubFoundry

[English version](README.md) | [Описание проекта](../README.ru.md)

Сайдкар является вспомогательным контейнером для стандартных установок
ClubFoundry через Docker Compose. Помимо проверяемых обновлений основного
приложения и пошаговых переходов между версиями, он выполняет откат,
самообновление, восстановление после сбоев, защиту от циклических падений и сбор
диагностики.

При обычной сетевой установке установщик развёртывает сайдкар автоматически.
Готовый офлайн-комплект из GitHub Release уже содержит образы основного
приложения и сайдкара и устанавливает их вместе в стандартном режиме Docker
Compose. Отдельно скачивать или устанавливать сайдкар не нужно.

ClubFoundry пока не опубликован в каталоге TrueNAS Apps. В коде предусмотрен
режим для будущей установки из каталога: в такой конфигурации сайдкар не
запускается, поскольку жизненным циклом образа управляет каталог.

- Образ: `ghcr.io/clubfoundry/updater`
- Среда: Linux-контейнер, amd64 и arm64
- API: HTTP на локальном порту `3001`; `/health` открыт для проверки состояния,
  все остальные методы требуют bearer-токен из общей папки данных
- Инструментарий: Go 1.26.5, только стандартная библиотека
- Средства контейнера: Alpine 3.24, Docker CLI 29.5.3 и Compose 5.4.0,
  зафиксированные по digest
- Лицензия: MIT, см. [`LICENSE.md`](LICENSE.md)
- Проверка выпуска: [`RELEASE_EVIDENCE.ru.md`](RELEASE_EVIDENCE.ru.md)

## Проверка и сборка

Быстрые проверки исходного кода без Docker:

```bash
cd sidecar
test -z "$(gofmt -l .)"
go vet ./...
go test -race -timeout 2m ./...
go build -trimpath -ldflags "-X main.version=v0.LOCAL" ./cmd/updater
```

Образ собирается из корня репозитория. Значение `VERSION` обязательно, потому
что после пересоздания контейнера самообновление проверяет версию бинарного
файла.

```bash
docker build \
  --build-arg VERSION=v0.LOCAL \
  -t ghcr.io/clubfoundry/updater:v0.LOCAL \
  sidecar/
```

В образ входят Docker CLI и Compose. Ему нужен доступ на запись к сокету Docker
хоста и к управляемому Compose-файлу, поэтому развёртывать его нужно только как
часть стека, созданного установщиком. Образ также содержит уведомления о
сторонних компонентах, зафиксированные тексты лицензий и предложение исходного
кода. Проверить этот комплект без Docker можно командой
`python sidecar/verify-release-evidence.py` из корня репозитория.

## Граница привилегий Docker

Доступ на запись к `/var/run/docker.sock` даёт контроль над Docker-демоном хоста
i должен считаться привилегией уровня хоста. Он нужен сайдкару для команд
жизненного цикла Compose, загрузки и маркировки проверенных образов, удаления
устаревших образов, одноразовых проверок миграций и замены собственного
контейнера.

Настроенная папка Compose и имена сервисов определяют управляемый стек. Команды
жизненного цикла применяются к этим сервисам. Очистка образов ограничена
настроенными репозиториями ClubFoundry и сохраняет образы, используемые любым
контейнером. При конфликте точного имени сайдкар проверяет принадлежность
контейнера и отказывается удалять его, если образ не соответствует правилу
ClubFoundry, используемому установщиком.

Кэш BuildKit относится ко всему демону, а не к одному репозиторию. Если
включена плановая очистка, применяется `docker buildx prune`. На сервере с
другими задачами сборки её можно отключить параметром
`auto_prune_buildcache_opt_out`. В предусмотренном для будущего каталога
TrueNAS Apps режиме этот контейнер не используется и доступ к Docker socket ему
не предоставляется.

## Проверка загружаемых артефактов

Загрузки с нескольких зеркал записываются в отдельные временные файлы. До
выполнения `docker load` SHA-256 обязан совпасть с опубликованным значением.
При резервной загрузке из registry применяется проверка registry. Образ, уже
имеющийся в локальном Docker под требуемым тегом, считается состоянием локального
демона и повторно не скачивается.

Загрузка с одного URL использует ту же границу: файл закрывается и сбрасывается
на диск, затем проверяется SHA-256, и только после этого начинается
`docker load`. Временный файл удаляется как после успеха, так и при ошибке.

## Поддерживаемая платформа

Поддерживается Linux-контейнер на amd64 или arm64. Требуются Docker CLI,
Compose, сокет `/var/run/docker.sock` и доступный для записи управляемый
Compose-файл. Проверки свободного места и сохранение владельца файлов используют
системные вызовы Linux. Сборки для других ОС предназначены только для локальной
разработки и тестов; неподдерживаемые проверки возвращают явный результат о
недоступности.

## HTTP-интерфейс

Клиентом API является основное приложение. Доступны группы методов для:

- состояния, конфигурации, занимаемого места, журналов, истории и диагностики;
- предварительной проверки, подготовки, применения, отмены, сброса, обновления
  и отката;
- самообновления контейнера и артефактов восстановления.

`GET /health` намеренно не требует аутентификации, чтобы Docker мог проверять
состояние. Все остальные методы требуют `Authorization: Bearer <token>`.
Запросы изменения образов возвращают `409 CATALOG_MANAGED`, когда
`CLM_UPDATE_MODE=truenas_apps`.

## Инварианты безопасности

1. Загруженный напрямую артефакт проверяется по SHA-256 до импорта образа.
2. Текущий образ сохраняется, пока новая версия не пройдёт проверку состояния.
3. Резервная копия базы включает `clm.db`, `clm.db-wal` и `clm.db-shm`.
4. В Linux восстановление сохраняет существующего владельца базы данных.
5. Пошаговый откат возвращается к последнему успешному шагу.
6. Обновление приложения и самообновление имеют раздельные состояния.
7. Операции Compose ограничены настроенными сервисами и проектом ClubFoundry;
   очистка образов ограничена настроенными репозиториями и не удаляет образ,
   используемый любым контейнером.
8. Установка из каталога не может менять жизненный цикл приложения через этот
   контейнер.

## Конфигурация

Установщик передаёт рабочую конфигурацию. Основные переменные для оператора:

| Переменная | Назначение |
|---|---|
| `CLUBFOUNDRY_UPDATER_ADDR` | Адрес HTTP; установщик привязывает порт 3001 к loopback. |
| `CLUBFOUNDRY_DATA_DIR` | Общая папка состояния и данных приложения. |
| `CLUBFOUNDRY_CLOUD_URL` | Базовый URL сервиса управления обновлениями. |
| `CLUBFOUNDRY_COMPOSE_DIR` | Папка управляемого Compose-файла. |
| `CLUBFOUNDRY_HEALTH_URL` | Метод проверки основного приложения. |
| `CLM_UPDATE_MODE` | `standalone` или `truenas_apps`; режим каталога запрещает изменение образов. |

Остальные переменные являются внутренними средствами восстановления и тестов.
Перед изменением настроек установщика изучите места их использования.

Установщик привязывает API к `127.0.0.1:3001`. Если
`CLUBFOUNDRY_UPDATER_ADDR` отсутствует, бинарный файл использует `:3001` и
слушает все интерфейсы. Не удаляйте заданное установщиком ограничение loopback.

## Участие в разработке

Не смешивайте изменения поведения с рефакторингом читаемости. Комментарии в
коде пишутся на английском и объясняют инварианты или неочевидные ошибки. Перед
отправкой изменения выполните команды проверки из начала этого файла.
